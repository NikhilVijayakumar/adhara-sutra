# Discovery model

Architecture discovery is the proposed development-time capability behind `adhara inspect`: it inspects application repositories and produces a structured, evidence-backed description of the implementation that exists. It must work for AdharaSutra-generated applications, existing applications that do not use AdharaSutra, partially migrated applications, standalone Python CLIs, Electron applications with Python backends, and applications using HTTP services, external CLI programs, SQLite persistence, background jobs, state, or multiple packages and entry points. The central principle: describe observed implementation, provide evidence for findings, and explicitly identify what cannot be determined. The engine shall not invent missing elements, treat a directory name as proof of a component's responsibility, treat an import as proof of runtime usage, claim behavioral correctness from static analysis, or silently promote uncertain patterns to verified facts.

Discovery is read-only by default: no source execution, no imports of application modules, no build-hook execution from reading `pyproject.toml` or `package.json`, traversal confined to approved roots, no network access, and caches treated as sensitive data. Mandatory analysis is deterministic without an LLM; optional AI-assisted interpretation stays advisory, local-first, and distinct from deterministic observations. Discovery describes; verification evaluates rules; migration plans changes — the three share contracts without duplicating analysis logic.

# What gets discovered

- Repository and identity — root, Git worktree, Python package and Electron project roots, workspaces, monorepos with independent application boundaries, nested repositories per explicit policy; non-Git repositories use normalized root identity and fingerprints. A revision includes commit, branch and worktree state; a dirty worktree is valid input the report must describe rather than claiming the committed revision only.
- Source inventory — eligible files (Python, TypeScript/JavaScript, manifests, configuration, requirements, test and profile metadata) with default exclusions (`.git`, `.venv`, `node_modules`, `__pycache__`, `dist`, `build`, coverage) and configurable extras, distinguishing intentional exclusion from failed analysis. Filesystem limits (size, file count, bytes, depth, duration) yield coverage warnings, never claims of completeness; symbolic links are recorded, safely resolved, prevented from escaping boundaries, cycle-detected and deduplicated.
- Modules and dependencies — imports, type references, instantiation, invocation, registration, configuration references, and dynamic dependencies recorded as unresolved; the graph distinguishes internal, framework, standard-library, third-party and unresolved imports; cycles are recorded as facts, with violation classification left to verification.
- Entry points — `if __name__ == "__main__"`, `__main__.py`, console scripts, CLI framework registrations, runtime bootstrap; CLI, worker, development and test entry points are not automatically production entry points. Each records identifier, location, invocation form, target, framework, confidence and evidence.
- CLI architecture — AdharaSutra action registration, argparse, Typer, Click, `sys.argv` handling, custom routers, JSON stdin parsing and stdout emission; command inventories carry name, registration source, handler, arguments, execution mode and service dependencies. A custom CLI is described, not judged invalid; dynamic registration carries uncertainty.
- Electron integration — main processes, preload scripts, renderer roots, IPC handlers and invoke calls, context-bridge exposure, child-process creation and bridge usage; communication patterns such as subprocess stdin/stdout, one-shot commands, persistent NDJSON, HTTP, custom sockets or the AdharaSutra bridge; IPC chains from renderer invocation through preload API, IPC handler and Python bridge to the entry point, with dynamic channel names left unresolved. `contextIsolation`, `nodeIntegration` and preload paths are recorded as observations only; security judgment belongs to verification and testing.
- External integrations — HTTP (HTTPX, Requests, aiohttp), WebSockets, subprocess patterns (`subprocess.run`, `subprocess.Popen`, `asyncio.create_subprocess_exec`, Electron `spawn`/`exec`), SQLite (`sqlite3.connect`, factories, ORM initialization) and filesystem access. Each connector records category, library, source locations, configuration references, lifecycle ownership, adapters and confidence; an import is evidence of a dependency, not proof of runtime initialization.
- State and jobs — module-level mutables, singletons, session and job stores, JSON/SQLite-backed settings, Electron-side synchronization; classifications (request, session, process, job, persistent, UI-only, unknown) require evidence, and ownership is recorded as observed, inferred or unknown. Jobs are found via `asyncio.create_task`, thread/process pools, worker classes, custom managers, queues and subprocess workloads, recording submission, handler, mechanism, state tracking, cancellation, results, persistence and owner; a persisted job table is not proof of durable execution, and a managed job is distinct from an OS process.
- Configuration and lifecycle — configuration files, environment variables, settings classes and loaders, with precedence confirmed only by implementation evidence; bootstrap, service initialization, startup and shutdown hooks, cleanup, signal handling and readiness checks. Identifying exception handlers does not prove runtime failure behavior.

# Discovery pipeline

The proposed pipeline has ten stages: resolve repository, load analysis policy, inventory source, parse source, analyze relationships, run detectors, collect evidence, normalize the model, validate completeness, produce output. Parsing is language-aware — Python via AST, TypeScript/JavaScript via a parser validated against realistic TypeScript syntax rather than JavaScript-compatible subsets, configuration via real JSON/YAML/TOML parsers that distinguish valid values, missing fields, unsupported structures, invalid syntax and dynamically computed values — and the engine shall not rely exclusively on regular expressions for language structure. Three modes are proposed: full discovery, incremental discovery (changed inputs plus invalidated dependents), and scoped discovery (selected packages, modules or concerns, clearly marked incomplete relative to full-project analysis).

Detectors are isolated, read-only, registry-based units declaring identifier, version, languages, applicable inputs, architectural concern, required facts, produced observations and known limitations; one detector failure must not discard other detectors' valid results, and detectors produce observations and evidence, never compliance verdicts. Custom detectors are trusted, versioned extensions following read-only, evidence, schema, resource and error contracts; ordinary discovery never imports detector implementations from the inspected repository.

# Evidence, confidence and coverage

Every source-derived finding references an evidence record: stable `evidence_id`, repository-relative `source_path`, `source_hash`, `start_line`/`end_line`, related `symbol`, `observation`, `detector_id` and `analysis_method`, pointing at the smallest useful source range. Findings classify as observed (directly supported by source syntax or configuration), inferred (derived from multiple observations) or unresolved, with proposed confidence levels high, medium, low or unknown — confidence is not correctness, and high confidence in a static observation does not prove runtime behavior. Conflicting detector interpretations are retained or resolved with documented evidence, never silently chosen for verification convenience. Evidence freshness ties to source fingerprints: changed files make prior evidence stale, and records must not be silently reused after their supporting source changes. Coverage is mandatory metadata with statuses (`analyzed`, `excluded`, `unsupported`, `parse_failed`, `skipped_limit`, `unresolved`, `not_checked`) reported by language, file category, package, architectural concern and detector; the verifier must consider coverage, and unexamined source must not be assumed compliant.

# Shared intermediate model

The primary output is the proposed versioned ApplicationArchitecture model: schema version, repository identity, source snapshot, analysis metadata and coverage, plus applications, packages, modules, dependencies, entry points, CLI commands and routing, Electron components and IPC relationships, connectors, external dependencies, processes, persistence, state, jobs, configuration, lifecycle, relationships, evidence, unresolved references and analysis diagnostics — JSON-serializable with stable field definitions, explicit relationships, an unknown-versus-absent distinction, and validation before downstream consumption. Entity identifiers are deterministic per source snapshot (entity kind, package namespace, qualified symbol name, relative path); persistent identity across renames is not claimed without a supported matching mechanism, and duplicate observations from multiple detectors are normalized without losing separate evidence. The model is explicitly the current implementation — distinct from target architecture, verification results and migration plans — and discovery must not silently populate a target architecture by assuming the existing implementation is correct.

# Caching and incremental analysis

Cacheable results include file fingerprints, parsed syntax facts, import relationships, detector observations, evidence records and model fragments, keyed by source content fingerprint, parser version, detector version, discovery configuration and dependency context. Changed files invalidate their facts and dependent findings; deleted files never remain as current observations; renames update paths, with content-based reuse only where current evidence reflects the new snapshot; changes to configuration, exclusions, parser options or detector versions invalidate cached analysis even when source is unchanged. Because files may change mid-analysis, content fingerprints are validated before finalization — the engine may retry within bounded limits, report a partial or inconsistent snapshot, or require a new scan, never silently blending incompatible source states. Incremental results must be semantically equivalent to full discovery within the supported analysis contract, verified by equivalence tests; a full rescan remains available and the correctness reference.

# Reporting output

Proposed reports cover architecture inventory, dependency summary, CLI architecture, Electron integration, connector inventory, state and job inventory, configuration and lifecycle, unresolved findings, and analysis coverage, as developer-readable Markdown or machine-readable JSON preserving entities and evidence references. Reports identify analysis mode, source snapshot, scope, languages, detectors used, coverage, findings and unresolved areas, prefer repository-relative paths, and redact credentials, secrets, private configuration and unrelated source snippets. Proposed CLI forms: `adhara inspect <path>` with `--format json|markdown`, `--focus <concern>`, `--incremental`, `--full` and explicit `--output`; exit statuses distinguish complete success, partial success, invalid inputs, repository access failure, unsupported requests and internal failure. Discovery reports never label an implementation compliant or noncompliant — that requires explicit verification rule evaluation.

# Alternatives considered

Proposed: read-only static analysis as the default mode; AST-based Python analysis, with LibCST evaluated only where detectors need precise syntax preservation; a TypeScript parser chosen by parsing fidelity, distribution complexity and dependency isolation rather than staying inside one language runtime; language-specific configuration parsers; a shared intermediate model with versioned JSON serialization; observed/inferred/unresolved classification with qualitative confidence levels; mandatory coverage metadata; revision-plus-worktree source identity; fingerprint-and-dependency invalidation; trusted, versioned custom detectors; optional, explicitly authorized runtime observation; no LLM dependency; Markdown and JSON reporting; verification and migration as separate owning modules. Deferred: runtime instrumentation until the static model and safety contracts validate; advisory-only AI classification; cross-revision entity identity matching; a dedicated dependency-graph library in favor of a lightweight internal representation; embedded source snippets in favor of references, ranges and fingerprints; caches outside the inspected repository by default.

# Open questions

- AD-OQ-001 — Python parsing technology: standard AST alone, or LibCST for richer source metadata?
- AD-OQ-002 — TypeScript parsing: Node-based compiler service or a parser usable directly from Python?
- AD-OQ-003 — Dedicated dependency-graph library or a lightweight internal representation?
- AD-OQ-004 — Should entity identifiers persist across file moves and renames?
- AD-OQ-005 — Qualitative confidence levels or numeric scores?
- AD-OQ-006 — Should discovery caches be stored inside the inspected repository?
- AD-OQ-007 — Should incremental refresh be supported in the first release?
- AD-OQ-008 — Should multiple applications in one repository share a single architecture model?
- AD-OQ-009 — Should optional runtime instrumentation be implemented initially?
- AD-OQ-010 — Should AI-assisted architectural classification be supported?
- AD-OQ-011 — Should the architecture model embed full source snippets?
- AD-OQ-012 — Should AdharaSutra-specific detection rules be embedded in discovery?
- AD-OQ-013 — Should the engine recognize existing behavioral and integration tests?
- AD-OQ-014 — How should repositories containing C++, Rust or other unsupported languages be handled?
- AD-OQ-015 — Should discovery reports automatically include raw source excerpts?
