# 1. Purpose

This document defines the architecture of AdharaSutra's Project Scaffolding subsystem.

The scaffolder enables developers to create new applications that already follow AdharaSutra's approved application architecture.

It shall generate consistent application structures, bootstrap code, configuration, selected infrastructure registrations, testing foundations, and documentation.

Scaffolding must minimize repetitive setup without forcing unnecessary layers or optional dependencies on every project.

The subsystem must remain independent of consuming application business functionality.

## 1.1 Objectives

The scaffolding architecture shall:

1. Generate new AdharaSutra applications from approved profiles.
2. Support different application architecture styles.
3. Generate valid framework bootstrap code.
4. Provide consistent CLI action registration.
5. Support optional Electron integration.
6. Include only selected framework capabilities.
7. Generate configuration using approved framework schemas.
8. Establish dependency and service composition boundaries.
9. Generate representative tests.
10. Generate minimum application documentation.
11. Provide deterministic, reproducible output.
12. Validate generated files before writing.
13. Avoid unintentionally overwriting existing projects.
14. Track template provenance and ownership.
15. Support controlled template evolution.
16. Integrate with architecture verification.
17. Produce machine-readable generation reports.
18. Remain suitable for automation and coding agents.
19. Support Windows, Linux, and macOS.
20. Provide a foundation for creating reusable application templates.

## 1.2 Central Principle

**A project generated by AdharaSutra must already conform to the architecture that AdharaSutra expects applications to follow.**

The scaffolder shall not generate independent implementations of infrastructure already owned by the framework.

## 1.3 Non-Goals

The initial scaffolder is not intended to:

- Generate complete business applications from natural-language descriptions.
- Invent domain entities or business requirements.
- Replace software architecture design.
- Automatically deploy applications to production.
- Automatically purchase or install external tools.
- Download large AI models without explicit authorization.
- Require an LLM.
- Require cloud services.
- Automatically modify arbitrary existing projects.
- Maintain every generated file indefinitely.
- Introduce a mandatory DDD structure into minimal applications.
- Generate custom implementations of framework infrastructure.
- Guarantee that generated business placeholders are production-ready.

Existing-application transformation belongs primarily to the Migration subsystem.

# 2. Architectural Principles

## PS-001 — Framework-First Generation

Generated applications shall use AdharaSutra's application runtime, registration mechanisms, and supported infrastructure interfaces.

## PS-002 — Profile-Driven Architecture

Application structure shall be determined by a selected architecture profile and explicitly enabled capabilities.

## PS-003 — Minimal Generation

The scaffolder shall not generate unnecessary layers, services, connectors, or dependencies.

## PS-004 — Shared Architecture Definitions

The scaffolder and architecture verifier shall use consistent versioned architecture-profile definitions.

## PS-005 — Declarative Generation

Template selection and generation rules should be represented through inspectable, versioned metadata.

## PS-006 — Deterministic Output

Identical generation inputs, template versions, and relevant environment constraints shall produce equivalent application artifacts, excluding explicitly variable metadata.

## PS-007 — Non-Destructive Defaults

The scaffolder shall never silently overwrite unrelated existing files.

## PS-008 — Generated-File Ownership

Generated application code becomes application-owned unless explicitly designated as a framework-managed artifact.

## PS-009 — Explicit Capability Selection

Only declared connector and runtime capabilities shall be configured.

## PS-010 — Secure Generation

User inputs shall be validated before use in paths, code identifiers, configuration, or shell commands.

## PS-011 — Validation Before Completion

Generated applications shall be structurally validated and have applicable baseline checks executed or explicitly reported as not executed.

## PS-012 — Testable Templates

Templates shall have automated generation and verification tests.

## PS-013 — Cross-Platform Portability

Generated applications shall avoid unnecessary operating-system assumptions.

## PS-014 — No Mandatory LLM

Scaffolding shall work deterministically without AI-assisted code generation.

## PS-015 — Incremental Evolution

Template upgrades shall be handled through explicit, reviewable migration operations rather than uncontrolled regeneration.

## 3.1 Main Architectural Separation

The scaffolder owns:

- How project structures are selected.
- How templates are rendered.
- How generated files are validated and written.
- How generation results are reported.

Architecture profiles own:

- Which structural rules apply.
- Which capabilities are permitted or required.
- Which dependency constraints exist.

The architecture verifier owns:

- Evaluating whether generated projects conform to those rules.

The consuming application owns:

- Its generated business-facing source files.
- Subsequent application implementation.
- Business entities and workflows.
- Application-specific configuration and tests.

# 4. Scaffolding Subsystems

The architecture contains eight logical subsystems.

| Subsystem | Responsibility |
|---|---|
| Input Validation | Validate names, paths, options, and identifiers |
| Profile Registry | Discover and resolve architecture profiles |
| Capability Resolver | Resolve supported module and integration combinations |
| Template Registry | Register versioned templates and template assets |
| Generation Planner | Produce a deterministic generation plan |
| Template Renderer | Create rendered source and configuration files |
| File Writer | Apply generated files safely |
| Validation and Reporting | Verify results and produce generation evidence |

These responsibilities may be implemented in fewer physical Python modules if that simplifies maintenance.

# 6. Architecture Profiles

## 6.1 Purpose

Architecture profiles determine the structural conventions and applicable requirements for generated applications.

## 6.2 Supported Initial Profiles

| Profile | Purpose | Complexity |
|---|---|---|
| `minimal` | Small utilities and simple applications | Low |
| `cli` | Standard multi-action Python CLI applications | Low–Medium |
| `ddd` | Domain-heavy applications | Medium–High |
| `electron-cli` | Electron-to-Python desktop applications | Medium |
| `ai-worker` | Processing-intensive applications | Medium–High |

## 6.3 Profile Composition

The architecture distinguishes a structural profile from optional capabilities.

A developer may choose:

- Primary structure: `ddd`.
- Interface: `electron-cli`.
- Capabilities: `jobs`, `process`, `sqlite`.

This avoids treating every combination as an entirely independent template.

## 6.4 Profile Definition

A profile should define:

- Profile identifier.
- Profile schema version.
- Description.
- Applicable application types.
- Required directories.
- Required modules.
- Required configuration.
- Required tests.
- Applicable architecture rules.
- Supported optional capabilities.
- Prohibited combinations.
- Default generated files.

## 6.5 Conceptual Profile Definition

```yaml
id: ddd
version: 1.0

description: Domain-driven application architecture

structure:
  required:
    - domain
    - application
    - infrastructure
    - interfaces
    - composition

rules:
  - APP-001
  - APP-003
  - APP-004
  - APP-005
  - APP-006

capabilities:
  optional:
    - http
    - websocket
    - process
    - sqlite
    - state
    - jobs
```

This is illustrative.

The final schema belongs in the architecture-profile design.

## 6.6 Profile Inheritance

Profiles may reuse common rule sets and template fragments.

Inheritance must be explicit and acyclic.

Profile composition must not silently override mandatory architectural rules.

## 6.7 Profile Versioning

A generated application must record the architecture-profile version used during creation.

# 7. Capability Selection

## 7.1 Purpose

Capabilities represent optional runtime or integration facilities.

## 7.2 Initial Capabilities

Proposed selectable capabilities:

```text
http
websocket
process
sqlite
filesystem
state
jobs
events
electron
```

Some capabilities may be automatically required by others.

For example:

- `electron` requires the CLI protocol and Electron bridge.
- `jobs` requires the relevant execution and state contracts.
- Persistent state requires a configured persistence adapter.
- Process-based jobs require process execution facilities.

These are capability relationships, not necessarily requirements to install every concrete connector.

## 7.3 Capability Descriptor

Each capability should specify:

- Identifier.
- Description.
- Dependencies.
- Optional packages.
- Generated configuration.
- Generated source files.
- Required service registrations.
- Applicable architecture rules.
- Generated test fixtures.
- Conflict constraints.

## 7.4 Capability Resolution

The resolver shall detect:

- Unsupported capabilities.
- Missing dependencies.
- Invalid combinations.
- Dependency cycles.
- Unsupported profile/capability combinations.

## 7.5 Auto-Selected Dependencies

Required transitive capabilities may be selected automatically, but the generation plan must show them explicitly.

## 7.6 Optional Dependencies

Unused capabilities must not appear in project dependency declarations or startup registration merely because templates exist for them.

# 8. Scaffolding Input Model

## 8.1 Purpose

Scaffolding inputs define the intended generated project.

## 8.2 Required Inputs

At minimum:

- Project name.
- Target directory.
- Architecture profile.

## 8.3 Optional Inputs

- Python package name.
- CLI command name.
- Application description.
- Python version constraint.
- Runtime execution mode.
- Selected capabilities.
- Electron integration.
- Testing options.
- Configuration environment.
- Package metadata.
- Template version.
- License selection.

## 8.4 Conceptual Input

```json
{
  "project_name": "vani",
  "package_name": "vani",
  "target_directory": "./vani",
  "architecture_profile": "ddd",
  "interfaces": ["electron-cli"],
  "capabilities": [
    "process",
    "sqlite",
    "state",
    "jobs"
  ],
  "python_version": "3.12"
}
```

This example defines a generated application configuration, not an existing project state.

## 8.5 Input Normalization

Project names may need normalization for different naming contexts.

Examples:

| Context | Example |
|---|---|
| Display name | My Audio Studio |
| Distribution name | my-audio-studio |
| Python import package | my_audio_studio |
| CLI command | my-audio-studio |
| Application identifier | my-audio-studio |

The scaffolder must not assume all names follow the same character rules.

## 8.6 Name Collisions

The generator shall detect collisions with:

- Python keywords.
- Invalid package identifiers.
- Existing project files.
- Reserved framework namespaces.
- Unsupported filesystem names.

## 8.7 Input Security

Inputs must not be evaluated as executable template code.

Paths must be validated before filesystem operations.

# 9. Project Naming and Identity

## 9.1 Project Identity

Each generated application shall have a stable application identifier.

## 9.2 Naming Properties

Names should support:

- Human-readable display names.
- Python import identifiers.
- Package distribution identifiers.
- CLI entry point names.
- Electron application identifiers.

## 9.3 Independent Applications

Different applications must not accidentally share:

- Runtime configuration.
- Persistent state paths.
- Log directories.
- Cache directories.
- Artifact storage.
- Connector instances.

## 9.4 Renaming

Application renaming after generation is a separate migration concern.

The scaffolder should not promise that changing a project name automatically migrates all existing data paths or package references.

## 9.5 Generated Metadata

Generated metadata should record both the original input and normalized identifiers.

# 10. Template Architecture

## 10.1 Purpose

Templates define the reusable source and configuration fragments used to generate applications.

## 10.2 Template Categories

The template registry may include:

- Base project.
- Core bootstrap.
- CLI actions.
- DDD structure.
- Connector registration.
- State.
- Jobs.
- Electron bridge integration.
- Tests.
- Documentation.
- Packaging metadata.

## 10.3 Template Fragments

Templates should be composable.

For example:

```text
Base Project Template
          │
          ├── CLI Template
          │
          ├── DDD Template
          │
          ├── Jobs Template
          │
          ├── Process Connector Template
          │
          └── Electron Template
```

## 10.4 Template Registry

Each template must have:

- Stable identifier.
- Version.
- Description.
- Compatible profile versions.
- Required capabilities.
- Input variables.
- File outputs.
- Content ownership policy.
- Validation requirements.

## 10.5 Template Rendering

The renderer may use a controlled text-template engine.

The exact rendering library is a detailed implementation decision.

Templates must not execute arbitrary Python code supplied through user input.

## 10.6 Conditional Content

Conditional generation should be driven by declared capabilities.

It must not depend on undocumented template naming assumptions.

## 10.7 Template Conflict Detection

Two templates must not silently write different content to the same destination.

Conflicts shall be resolved by explicit composition rules or rejected.

# 11. Template Manifest

## 11.1 Purpose

Each template bundle should provide a machine-readable manifest.

## 11.2 Proposed Manifest Fields

```yaml
template:
  id: application-base
  version: 1.0.0
  profile: minimal

variables:
  - project_name
  - package_name
  - application_id

files:
  - source: pyproject.toml.template
    destination: pyproject.toml
    ownership: application

  - source: app.py.template
    destination: src/{{ package_name }}/app.py
    ownership: application

  - source: test_app.py.template
    destination: tests/test_app.py
    ownership: application

validation:
  - python_syntax
  - bootstrap_contract
  - architecture_profile
```

This is conceptual.

The final manifest must have a formally validated schema.

## 11.3 File Ownership

Every generated file must have a declared ownership category.

## 11.4 File Conditions

The manifest should identify when an output is generated.

## 11.5 Manifest Integrity

The framework must detect invalid or incomplete template manifests before writing project files.

## 11.6 Template Provenance

Generation reports should include the exact template identifier and version used.

# 13. Framework Bootstrap Generation

## 13.1 Purpose

Every generated application shall have a valid AdharaSutra bootstrap.

## 13.2 Conceptual Bootstrap

```python
from adharasutra import Application

app = Application(
    name="my-app",
    version="0.1.0",
)


@app.action("application.ping")
async def ping(payload, context):
    return {"message": "pong"}


if __name__ == "__main__":
    app.run()
```

This is an illustrative public API shape.

The final scaffold must use the approved framework API, not these pseudocode signatures unless subsequently adopted.

## 13.3 Bootstrap Requirements

Generated bootstrap code shall:

- Use the framework runtime.
- Register application actions.
- Declare needed services.
- Avoid import-time side effects.
- Use framework configuration.
- Use approved lifecycle mechanisms.
- Avoid unnecessary connector initialization.

## 13.4 Execution Modes

The scaffold must generate an entry point compatible with its selected execution model.

Possible modes:

- One-shot CLI.
- Persistent CLI.
- Both.

## 13.5 Bootstrap Validation

A generated project shall be checked for valid imports, registration, and required runtime configuration.

# 14. Application Layer Generation

## 14.1 Domain Layer

The generator may create the domain package structure.

It must not invent business entities without explicit input or a selected example template.

## 14.2 Application Layer

The generator may provide:

- Example use case.
- Action interface.
- Application service placeholder.
- Port definition.
- Typed request/response placeholder.

## 14.3 Infrastructure Layer

Only infrastructure selected by capabilities should be generated.

For example, selecting `sqlite` may generate a sample repository adapter and migration directory.

## 14.4 Composition Root

The generator shall establish one clearly identifiable composition root.

## 14.5 Interface Layer

The generator shall use framework action registration.

It shall not implement custom stdin parsing or protocol response framing.

## 14.6 Example Code

Examples must be clearly identified as examples.

They must not imply production integrations are configured merely because placeholders were generated.

# 15. Connector Scaffolding

## 15.1 Purpose

Connector scaffolding supplies registration and application-adapter foundations.

## 15.2 HTTP Capability

May generate:

- HTTP connector configuration.
- Adapter placeholder.
- Port interface.
- Mock HTTP test fixture.

It shall not automatically generate ComfyUI-specific business operations unless an explicit integration template is selected.

## 15.3 External CLI Capability

May generate:

- Process connector registration.
- Executable configuration.
- Adapter placeholder.
- Controlled test executable fixture.
- Cancellation test structure.

Shell execution shall not be enabled by default.

## 15.4 SQLite Capability

May generate:

- SQLite configuration.
- Application repository structure.
- Migration directory.
- Test database fixture.

It shall not generate a complete domain schema without the necessary domain definition.

## 15.5 WebSocket Capability

May generate:

- Connection registration.
- Message adapter placeholder.
- Connection-lifecycle tests.

## 15.6 Filesystem Capability

May generate application-specific directory configuration and artifact-handling placeholders.

## 15.7 Connector Lifecycle

Generated application code must rely on framework lifecycle management rather than independently creating global connector instances at import time.

---

# 16. State Scaffolding

## 16.1 Purpose

State scaffolding establishes application state registration without inventing business state semantics.

## 16.2 Generated Capabilities

Depending on selection, generated code may include:

- State definition registration.
- Scope examples.
- State access examples.
- Optional persistent adapter configuration.
- State tests.

## 16.3 State Scopes

The generator must follow the approved state scope definitions:

- Request.
- Session.
- Process.
- Job.
- Persistent.

## 16.4 Persistence

Persistent state requires explicit backend configuration.

The scaffold must not install or configure SQLite merely because volatile state is enabled.

## 16.5 Domain Separation

Generated generic state examples must not encourage storing complete domain entities inside an unrestricted global state dictionary.

---

# 17. Job Scaffolding

## 17.1 Purpose

Job scaffolding generates the application-side structure required for managed long-running work.

## 17.2 Generated Components

Potential outputs:

- Job definition.
- Job registration.
- Application job handler.
- Progress reporting example.
- Cancellation-aware example.
- Job test fixture.
- Concurrency configuration.

## 17.3 Execution Strategy

The selected executor determines required capabilities.

Examples:

- Async.
- Thread.
- External process.

## 17.4 Durable Execution

The scaffold must not generate a claim of durable execution when only an in-process Job Manager is configured.

## 17.5 Persistence

Job metadata persistence remains optional.

## 17.6 Testing

Generated job tests should verify acceptance, execution, terminal status, and applicable cancellation behavior.

---

# 18. Electron Scaffolding

## 18.1 Purpose

Electron scaffolding creates the frontend integration foundation using the shared AdharaSutra Electron bridge.

## 18.2 Generated Layers

- Main process.
- Preload.
- Renderer.
- Backend client abstraction.
- Runtime configuration.
- Protocol integration tests.

## 18.3 Main Process

The main process shall own the bridge and Python process lifecycle.

## 18.4 Preload

The preload shall expose restricted application APIs.

## 18.5 Renderer

The renderer shall interact with registered Python actions through approved IPC operations.

## 18.6 Bridge Dependency

The generated Electron package shall depend on the shared bridge package.

It must not copy the bridge's entire transport implementation into the application.

## 18.7 Runtime Manifest

The generated project may include development and production runtime configurations.

Production paths must not assume a developer's local virtual environment exists on the end user's machine.

## 18.8 UI Framework

The bridge is UI-framework-independent.

A minimal Electron renderer may be generated initially.

React, Vue, or other renderer templates should be optional.

## 18.9 Security Defaults

Generated Electron applications should use:

- Context isolation.
- Restricted preload API.
- Renderer Node integration disabled.
- Authorized IPC handlers.
- Controlled Python process launch.

## 18.10 Generated Electron Tests

Tests should validate startup, handshake, request/response communication, and IPC boundaries.

# 20. Dependency and Package Generation

## 20.1 Python Packaging

Generated Python applications should use `pyproject.toml`.

## 20.2 Dependency Selection

The generated dependency set shall include:

- AdharaSutra runtime.
- Required optional capability dependencies.
- Application-specific dependencies explicitly selected.
- Development/testing dependencies where requested.

## 20.3 Dependency Isolation

Unused connector dependencies must not be included automatically.

## 20.4 Version Constraints

Dependency constraints shall follow the framework compatibility policy.

# 24. Filesystem Safety

## 24.1 Destination Validation

The scaffolder shall validate the output destination before writing.

## 24.2 Existing Directory Policy

The default policy shall reject generation into a nonempty destination when conflicts are possible, unless an explicitly supported safe mode is selected.

## 24.3 File Overwrite

Existing unrelated files shall never be overwritten silently.

## 24.4 Path Traversal

Template paths and user-controlled names must not escape the approved destination.

## 24.5 Symbolic Links

Destination path validation must account for symbolic links and resolved targets.

## 24.6 Partial Write Failure

If generation fails during application, the scaffolder should clean up files created during the current operation when doing so is safe.

It must not delete preexisting files.

## 24.7 Atomicity

The generator should use staging and atomic directory movement where supported.

It must not claim cross-platform atomicity when filesystem or destination conditions do not provide it.

## 24.8 File Permissions

Generated executable scripts and files must receive appropriate permissions for the target platform.

## 24.9 Security

The scaffolder shall not execute generated scripts without an explicit, documented verification or setup operation.

**When** generation completes,

**Then** the framework shall display planned files and dependencies.

**Then** the scaffolder shall refuse unsafe overwriting.

# 41. Outstanding Questions

## PS-OQ-001 — Default Profile

Should `adhara new` default to `minimal` or `cli`?

**Recommendation:** Use `minimal` by default, with explicit profile selection for complex applications.

## PS-OQ-002 — Profile Composition

Should `electron-cli` be a standalone profile or an interface capability layered onto `minimal`, `cli`, or `ddd`?

**Recommendation:** Treat it as a composable interface capability while preserving `electron-cli` as a convenient preset.

## PS-OQ-003 — Template Engine

Should templates use Jinja2 or a smaller custom renderer?

**Recommendation:** Evaluate template complexity first. Prefer established, sandboxed or restricted rendering facilities over developing a general-purpose template language.

## PS-OQ-004 — Interactive Wizard

Should the initial developer CLI include an interactive wizard?

**Recommendation:** Prioritize noninteractive commands and dry runs. Add an interactive wizard using the same engine.

## PS-OQ-005 — Profile Schema Ownership

Should profiles be maintained primarily by the scaffolder or verifier?

**Recommendation:** Use a shared architecture-profile contract owned by the architecture tooling foundation.

## PS-OQ-006 — Template Customization

Should organizations or applications supply custom templates?

**Recommendation:** Support controlled template extension after built-in template contracts stabilize.

## PS-OQ-007 — Dependency Installation

Should the scaffolder automatically run `pip install` or an Electron package manager?

**Recommendation:** Make installation a separate explicit option, disabled by default.

## PS-OQ-008 — Generated Documentation

How much documentation should minimal applications receive?

**Recommendation:** Generate a focused README and testing instructions. Avoid empty documentation folders.

## PS-OQ-009 — Example Business Actions

Should every project receive a sample `application.ping` action?

**Recommendation:** Include one minimal demonstrable action that can be removed after project setup.

## PS-OQ-010 — Generated Contract Types

Should Electron action types be generated from registered Python action schemas?

**Recommendation:** Support this after the action schema and CLI protocol contracts are stable.

## PS-OQ-011 — File Ownership Metadata

Should per-file hashes be recorded in generation metadata?

**Recommendation:** Consider hashes for provenance and future upgrades, but do not assume an unchanged hash grants permission to overwrite a file.

## PS-OQ-012 — Template Upgrade Command

Should the developer CLI provide `adhara scaffold upgrade`?

**Recommendation:** Defer automatic upgrades. Provide comparison and migration planning first.

## PS-OQ-013 — Generation Rollback

Should the scaffolder guarantee all-or-nothing generation?

**Recommendation:** Use staging and safe cleanup, but explicitly document limitations across filesystems and external setup operations.

## PS-OQ-014 — Application Profiles

Should profiles include desktop-specific packaging settings?

**Recommendation:** Separate application architecture from deployment/package configuration, then combine them through explicit selections.

## PS-OQ-015 — Template Test Coverage

Should every supported capability combination be tested?

**Recommendation:** Test baseline profiles, representative combinations, dependency boundaries, and known conflicts using a maintained compatibility matrix.

# 43. Final Architecture Summary

AdharaSutra's Project Scaffolding subsystem provides a standardized method for creating new Python applications that conform to the framework's architecture.

It supports:

- Profile-based project structures.
- Optional capability composition.
- Declarative templates.
- Validated application bootstrap.
- Framework-managed connector registration.
- State and job integration.
- Shared Electron bridge integration.
- Configuration generation.
- Package metadata.
- Testing foundations.
- Documentation.
- Deterministic generation.
- Safe filesystem operations.
- Architecture verification.
- Structured generation reports.

The scaffolder creates application foundations without inventing or taking ownership of domain-specific business logic.

Generated application source becomes application-owned.

Template changes do not automatically overwrite existing applications.

Scaffolding and architecture verification share common profile definitions, ensuring that generated projects are evaluated against the same standards used during development and migration.

The central guarantee is:

**Every generated application begins with a consistent, verifiable AdharaSutra foundation—containing only the architecture and capabilities it actually needs.**
