# 1. Purpose

This document defines the architecture of AdharaSutra's Architecture Verification subsystem.

The verification engine evaluates whether an application's existing implementation satisfies a selected, versioned architecture profile and its applicable architectural rules.

The engine consumes the evidence-backed intermediate architecture model produced by the Architecture Discovery subsystem.

It evaluates structural, dependency, integration, configuration, and other supported architectural constraints.

The verification engine must work with:

1. New applications generated by AdharaSutra.
2. Existing applications already using AdharaSutra.
3. Legacy applications being assessed for migration.
4. Partially migrated applications.
5. Standalone Python CLI applications.
6. Electron applications with Python backends.
7. Applications using HTTP, WebSocket, external CLI, SQLite, and filesystem integrations.
8. Applications using state and job infrastructure.
9. Multi-package repositories and monorepos.
10. Automated CI and coding-agent workflows.

## 1.1 Central Principle

**Architecture verification must evaluate declared rules against actual evidence. It must not infer compliance merely because no violation was discovered.**

Every verification result shall indicate:

- Which rule was evaluated.
- Which profile and rule version applied.
- What evidence was available.
- What the evaluation determined.
- What information was missing, if any.
- Whether an approved exception affects enforcement.
- What corrective action may be required.

## 1.2 Objectives

The subsystem shall:

1. Provide versioned architecture profiles.
2. Define machine-readable architecture rules.
3. Evaluate rules deterministically.
4. Consume the shared discovery model.
5. Support structural and dependency checks.
6. Verify framework integration conventions.
7. Distinguish static verification from runtime validation.
8. Preserve source evidence.
9. Identify violations and their severity.
10. Support partial and uncertain analysis.
11. Support explicit exceptions.
12. Support incremental-migration baselines.
13. Prevent new violations during migration.
14. Produce actionable Markdown and JSON reports.
15. Support automation-friendly exit codes.
16. Integrate with CI pipelines.
17. Support cross-harness coding-agent workflows.
18. Remain independent of LLM inference.
19. Support profile and rule evolution.
20. Avoid modifying application source during verification.

# 2. Scope and Non-Goals

## 2.1 In Scope

The architecture includes:

- Architecture profile definitions.
- Rule catalogs and rule contracts.
- Rule applicability.
- Rule severity.
- Deterministic evaluation.
- Evidence requirements.
- Coverage-aware results.
- Architectural dependency verification.
- Framework adoption checks.
- CLI protocol integration checks.
- Electron architecture checks.
- Connector usage checks.
- State and job architecture checks.
- Configuration and lifecycle checks.
- Security-oriented static checks.
- Test-evidence integration.
- Rule exceptions and waivers.
- Migration baselines.
- Incremental verification.
- Report generation.
- CI integration.
- Agent-readable output.
- Verification-engine testing.

## 2.2 Out of Scope

The initial verification engine shall not:

- Prove business logic correctness.
- Prove runtime behavior from static source inspection alone.
- Replace unit or integration tests.
- Automatically rewrite violating source.
- Automatically approve architecture exceptions.
- Automatically waive security requirements.
- Assume a repository is compliant because a scan completed.
- Infer every dynamic dependency.
- Execute arbitrary project code during default static verification.
- Depend on external AI services.
- Require a running Electron application.
- Guarantee detection of every security vulnerability.
- Replace a dedicated security scanner.
- Replace source-formatting or ordinary linting tools.

The Migration subsystem may consume findings and propose modifications.

Actual source transformation remains outside the verifier's responsibility.

# 3. Architecture Verification Principles

## AV-001 — Separation from Discovery

Discovery describes implementation facts.

Verification evaluates those facts against architecture rules.

## AV-002 — Evidence-Based Decisions

Every reported violation shall have supporting evidence or clearly identified failed verification evidence.

## AV-003 — No False PASS

A rule must not pass solely because relevant analysis was incomplete or unavailable.

## AV-004 — Deterministic Evaluation

Given equivalent discovery facts, profile versions, rule versions, and relevant configuration, the verifier shall produce equivalent canonical results.

## AV-005 — Versioned Architecture Contracts

Profiles and rules shall have explicit identifiers and versions.

## AV-006 — Profile-Scoped Applicability

Rules shall apply according to the application's declared or explicitly selected architecture profile.

## AV-007 — Explicit Exceptions

Exceptions shall require identifiable scope, justification, ownership, and an approval policy.

## AV-008 — Migration Baseline Isolation

A migration baseline shall not be confused with full architectural compliance.

## AV-009 — Read-Only Verification

Ordinary verification shall not modify the inspected application.

## AV-010 — No Mandatory LLM

Architecture verification shall function without AI assistance.

## AV-011 — Actionable Reporting

Violations shall identify the affected architecture boundary and proposed remediation direction.

## AV-012 — CI Suitability

Results shall support automated pass/fail decisions using documented enforcement policies.

## AV-013 — Security Rule Protection

Mandatory security constraints shall not be disabled through ordinary application-controlled exception mechanisms.

## AV-014 — Coverage Transparency

Verification shall report the analysis and evidence coverage relevant to each rule.

## AV-015 — Independent Application Support

The verifier shall support multiple applications and packages within one repository.

## AV-016 — No Implicit Runtime Proof

Static analysis shall not claim runtime behavior was verified unless compatible executable evidence was actually collected.

## AV-017 — Explicit Rule Dependencies

Rules shall declare which discovery facts, analyses, or test evidence they require.

## AV-018 — Explainable Outcomes

A developer shall be able to understand why a rule passed, failed, or could not be evaluated.

# 6. Verification Inputs

## 6.1 Required Inputs

Every verification execution requires:

1. An ApplicationArchitecture model or sufficient discovery input to produce one.
2. A selected architecture profile.
3. Compatible profile and rule definitions.
4. A verification policy.
5. Evidence metadata.
6. Discovery coverage information.

## 6.2 Optional Inputs

Optional inputs may include:

- Test execution results.
- Approved exception records.
- Migration baseline.
- Historical verification results.
- Additional trusted runtime observations.
- Custom rule packages.
- CI enforcement configuration.

## 6.3 Input Integrity

The verifier shall validate:

- Model schema version.
- Profile version.
- Rule compatibility.
- Evidence references.
- Source snapshot identity.
- Applicable configuration schema.

Invalid or incompatible inputs must not silently produce a successful verification result.

## 6.4 Source Freshness

The verifier must confirm that the architecture model corresponds to the intended source snapshot.

If evidence is stale, affected rules shall not receive unsupported PASS outcomes.

## 6.5 Direct Repository Verification

The developer CLI may invoke discovery automatically before evaluating rules.

However, discovery and verification remain separate logical operations.

# 7. Architecture Profile Model

## 7.1 Purpose

An architecture profile defines the standards an application is expected to follow.

## 7.2 Profile Properties

Every profile should declare:

- Unique identifier.
- Version.
- Description.
- Architecture style.
- Required modules or layers.
- Applicable rules.
- Optional capability rules.
- Prohibited dependencies.
- Required tests.
- Severity overrides where permitted.
- Compatibility constraints.

## 7.3 Initial Profiles

| Profile | Purpose |
|---|---|
| `minimal` | Small utilities using AdharaSutra |
| `cli` | Standard Python CLI applications |
| `ddd` | Domain-driven applications |
| `electron-cli` | Electron-integrated applications |
| `ai-worker` | Applications using managed jobs and processing infrastructure |

## 7.4 Profile Composition

The architecture shall distinguish:

- Structural architecture profile.
- Interface capabilities.
- Runtime capabilities.

Example:

```yaml
architecture:
  structure: ddd

  interfaces:
    - electron-cli

  capabilities:
    - process
    - sqlite
    - state
    - jobs
```

The structure above is illustrative.

It is not a finalized profile-configuration schema.

## 7.5 Profile Applicability

A DDD profile may require strict domain dependency boundaries.

A minimal profile must not fail because it lacks unused DDD folders.

An Electron interface profile may require the shared bridge and secure IPC boundaries.

An application without jobs shall not receive job-specific verification failures solely because job infrastructure was not selected.

## 7.6 Profile Versioning

A profile's identity and version must be recorded in verification results.

Upgrading a profile may introduce or modify applicable rules.

The verifier shall make such changes visible.

# 8. Shared Profile Definitions

## 8.1 Purpose

The scaffolder and verifier must agree on what constitutes a valid application profile.

## 8.2 Shared Contract

Both subsystems shall consume compatible versioned profile definitions.

The scaffolder uses profile metadata to determine what to generate.

The verifier uses it to determine what to check.

## 8.3 Separation of Execution

The shared definition does not mean scaffolding and verification are the same implementation.

Their responsibilities remain separate.

## 8.4 Profile Consistency

A project generated using an approved profile should pass the corresponding structural checks before application-specific business code is added.

## 8.5 Template Compatibility

Template versions must declare compatible architecture profile versions.

A generated project must not silently claim compliance with a profile version its template was never designed to satisfy.

# 9. Architecture Rule Model

## 9.1 Purpose

Architecture rules represent testable constraints.

## 9.2 Rule Definition Fields

Each rule shall identify:

| Field | Purpose |
|---|---|
| `id` | Stable rule identifier |
| `version` | Rule definition version |
| `title` | Human-readable rule name |
| `description` | Expected architectural constraint |
| `category` | Rule classification |
| `severity` | Impact of violation |
| `applicability` | Profiles and capabilities to which it applies |
| `evidence_requirements` | Required discovery facts or test evidence |
| `evaluation_method` | Deterministic evaluator |
| `remediation` | Recommended correction |
| `exception_policy` | Whether and how exceptions are permitted |
| `enforcement` | Whether failure blocks the configured gate |

## 9.3 Conceptual Rule Definition

```yaml
id: APP-004
version: 1.0.0

title: Domain layer must not depend on infrastructure

category: dependency-boundary
severity: error

applies_to:
  structures:
    - ddd

requires:
  - module_inventory
  - resolved_import_graph
  - dependency_coverage

evaluation:
  type: forbidden_dependency
  from: domain
  to: infrastructure

exceptions:
  allowed: true
  approval_required: true

remediation:
  summary: Introduce an application or domain port
```

This definition is illustrative.

The finalized rule schema must specify the permitted evaluation operators and type constraints.

## 9.4 Rule Stability

A stable rule ID shall not be repurposed to represent an unrelated architectural constraint.

## 9.5 Rule Evolution

Changes that materially alter rule interpretation must use an appropriate rule-version update.

## 9.6 Declarative Rules

Common structural checks should use declarative operators.

Custom rule implementations may be necessary for more complex patterns.

Custom code must follow trusted plugin and compatibility policies.

# 10. Rule Categories

The framework should support the following categories.

| Category | Examples |
|---|---|
| Structure | Required modules and package organization |
| Dependency | Allowed import directions |
| Runtime | Application bootstrap and lifecycle |
| CLI | Action registration and protocol boundaries |
| Electron | Main/preload/renderer separation |
| Connector | Approved infrastructure access |
| State | Scope ownership and persistence |
| Job | Managed execution and cancellation |
| Configuration | Schema and capability declarations |
| Security | Dangerous subprocess or IPC patterns |
| Testing | Required test contracts and execution evidence |
| Packaging | Runtime dependency separation |
| Documentation | Required application documentation |

## 10.1 Rule Applicability

Not every category applies to every application.

Applicability must be resolved before evaluation.

## 10.2 Cross-Cutting Rules

Some rules apply to every application profile.

Examples may include:

- Framework runtime adoption.
- Public contract compatibility.
- Unsafe arbitrary command execution.
- Required bootstrap correctness.

## 10.3 Conditional Rules

Other rules apply only when their relevant capability is enabled.

For example:

- SQLite rules apply to applications using SQLite.
- Electron bridge rules apply to Electron applications.
- Job-management rules apply to applications using managed jobs.

# 11. Rule Evaluation Architecture

## 11.1 Evaluation Pipeline

```text
Load Architecture Model
        │
        ▼
Resolve Profile
        │
        ▼
Resolve Applicable Rules
        │
        ▼
Validate Rule Dependencies
        │
        ▼
Evaluate Evidence Coverage
        │
        ▼
Execute Deterministic Evaluators
        │
        ▼
Resolve Exceptions
        │
        ▼
Compare Migration Baseline
        │
        ▼
Aggregate Results
        │
        ▼
Produce Verification Report
```

## 11.2 Evaluation Order

Rules without dependencies may execute independently.

Rules relying on prerequisite findings must execute after their dependencies have been resolved.

## 11.3 Determinism

Equivalent input facts and policies must produce equivalent canonical verdicts.

Timestamps and execution-specific report metadata may differ without changing verdict meaning.

## 11.4 Evaluation Isolation

A failed custom evaluator should not automatically invalidate unrelated valid results.

Affected rules must report their inability to complete.

## 11.5 Read-Only Behavior

The evaluator shall not modify source files or install project dependencies.

# 12. Verification Outcomes

## 12.1 Canonical Outcomes

Each applicable rule shall produce one of four verdicts:

- `PASS`
- `FAIL`
- `NEEDS_REVIEW`
- `NOT_CHECKED`

## 12.2 PASS

The available evidence satisfies the rule's declared proof requirements within the analyzed scope.

PASS does not mean the entire application is defect-free.

## 12.3 FAIL

The available evidence establishes a violation of the rule.

A FAIL finding must identify the failing condition and supporting evidence.

## 12.4 NEEDS_REVIEW

Available evidence is relevant but insufficient, ambiguous, or conflicting, and a judgment requires additional inspection.

Examples:

- Dynamically constructed IPC channels.
- Reflection-based imports.
- Unclear resource ownership.
- Conditional initialization not resolvable statically.

## 12.5 NOT_CHECKED

The rule could not be evaluated or was not executed.

Examples:

- Required parser unavailable.
- Test runner not executed.
- Detector failed.
- Source excluded by analysis scope.
- Unsupported verification method.

## 12.6 Nonapplicable Rules

Rules that do not apply should be recorded as `not_applicable` in evaluation metadata or an applicability summary.

`not_applicable` is not a fifth compliance verdict.

A rule that does not apply must not inflate the PASS count.

## 12.7 Comparison

| Outcome | Evidence condition | Meaning |
|---|---|---|
| PASS | Sufficient and supports rule | Constraint satisfied within scope |
| FAIL | Sufficient and establishes violation | Constraint violated |
| NEEDS_REVIEW | Relevant but ambiguous | Human or additional analysis needed |
| NOT_CHECKED | Required analysis unavailable or unexecuted | No verdict established |

# 13. Coverage-Aware Evaluation

## 13.1 Problem

An absence of detected violations is not proof of compliance when source analysis is incomplete.

## 13.2 Coverage Requirements

Every rule must identify which discovery capabilities it requires.

Examples:

- Import graph.
- Python syntax analysis.
- TypeScript IPC analysis.
- Connector call detection.
- Configuration parsing.
- Test execution evidence.

## 13.3 Coverage Assessment

Before a rule passes, the verifier shall establish that the applicable analysis coverage meets that rule's proof requirements.

## 13.4 Coverage Failure

When required source cannot be analyzed, the result shall be NEEDS_REVIEW or NOT_CHECKED according to the available evidence.

## 13.5 Partial Violation Detection

A clear observed violation may receive FAIL even when other relevant source remains unanalyzed.

The report must still identify incomplete overall coverage.

## 13.6 Rule-Specific Coverage

Coverage shall be assessed at the narrowest meaningful scope.

A failure to parse an unrelated documentation utility should not automatically invalidate a rule evaluating a fully analyzed domain package.

## 13.7 Coverage Evidence

The report should identify:

- Required analysis.
- Actual coverage.
- Missing source or facts.
- Resulting confidence limitations.

# 14. Structural Verification

## 14.1 Purpose

Structural rules verify project organization and required framework integration points.

## 14.2 Typical Checks

Examples:

- Valid application bootstrap exists.
- Required architecture layers exist.
- Composition root is identifiable.
- Package metadata is valid.
- Selected capabilities have configuration.
- Required test directories or contracts exist.

## 14.3 Profile Sensitivity

Structural requirements must respect the selected architecture profile.

For example, a minimal application shall not be required to contain empty DDD layers.

## 14.4 Directory Names

Directory presence alone is not sufficient to establish architecture correctness.

The verifier should combine structural evidence with relevant import or registration evidence.

## 14.5 Missing Required Structure

A missing mandatory component may produce FAIL when source inventory coverage is sufficient.

# 15. Dependency Boundary Verification

## 15.1 Purpose

Dependency rules verify that source modules follow allowed architectural dependency directions.

## 15.2 DDD Example

```text
interfaces
    │
    ▼
application
    │
    ▼
domain
    ▲
    │
infrastructure
```

The infrastructure layer may implement application-defined ports while depending on domain models where necessary.

The composition root may depend on all layers because it wires implementations together.

## 15.3 Prohibited Dependencies

Examples:

- Domain importing concrete infrastructure.
- Domain importing Electron.
- Domain importing CLI protocol serialization.
- Application services importing concrete repository implementations.
- Framework core importing consuming application modules.

## 15.4 Dependency Rule Example

**Rule:** Domain modules must not import infrastructure modules.

**Observed evidence:**

```python
from my_app.infrastructure.database import Database
```

If found inside a domain module, this directly supports a violation of the rule.

## 15.5 Indirect Dependencies

The verifier should support checking both direct and transitive dependencies where the selected rule requires them.

## 15.6 Dynamic Dependencies

Unresolved dynamic imports shall not be silently assumed harmless.

## 15.7 Dependency Cycles

Cycles may be detected and evaluated according to profile-specific constraints.

## 15.8 Composition Exceptions

Approved composition roots must be identified explicitly.

An ordinary application module must not claim unrestricted dependency permissions simply by being named `composition.py`.

# 16. Framework Runtime Verification

## 16.1 Purpose

Verify that consuming applications use AdharaSutra's runtime and extension interfaces correctly.

## 16.2 Possible Checks

- Application definition exists.
- Runtime bootstrap uses approved APIs.
- Actions register through the framework.
- No competing protocol engine exists in normal application paths.
- Required lifecycle configuration is present.
- Optional capabilities are declared appropriately.
- Framework internal APIs are not imported where prohibited.

## 16.3 Runtime Limits

Static analysis may confirm registration syntax.

It cannot guarantee that the application starts correctly.

Startup behavior requires actual runtime smoke tests.

## 16.4 Required Runtime Evidence

A profile may require an executed startup test before the corresponding runtime-readiness rule can pass.

---

# 17. CLI Protocol Verification

## 17.1 Purpose

Verify that applications follow the approved CLI communication architecture.

## 17.2 Static Checks

Examples:

- Application actions use framework registration.
- Protocol serialization is not duplicated in application handlers.
- Known direct stdout writes are identified.
- Reserved action identifiers are not overridden.
- Protocol contracts use supported schemas.

## 17.3 Runtime Checks

Executable contract tests may validate:

- Request envelope processing.
- Response envelope correctness.
- Error serialization.
- Concurrent requests.
- Progress event delivery.
- Cancellation semantics.
- Protocol stdout isolation.

## 17.4 stdout Rule

Detectable raw output on protocol stdout should be reported.

However, static analysis cannot prove that arbitrary third-party code never writes to stdout.

## 17.5 Unknown Behavior

If protocol behavior cannot be verified, relevant runtime rules remain NOT_CHECKED or NEEDS_REVIEW.

---

# 18. Electron Architecture Verification

## 18.1 Purpose

Verify Electron main, preload, renderer, and Python communication boundaries.

## 18.2 Static Checks

Potential checks include:

- Python process creation occurs through approved main-process integration.
- Renderer does not directly spawn Python.
- Shared bridge dependency is present.
- Preload exposes restricted APIs.
- IPC registrations follow approved conventions.
- Context isolation is configured.
- Renderer Node integration is disabled where required.
- No competing Python communication layer is detected in the supported analysis scope.

## 18.3 Dynamic IPC

Computed IPC channel names may be unresolved.

The verifier must not claim a complete IPC relationship graph when discovery cannot resolve the channels.

## 18.4 Runtime Tests

Electron integration tests may verify:

- Handshake.
- Request routing.
- Process ownership.
- Renderer authorization.
- Event subscriptions.
- Renderer reload.
- Shutdown.

## 18.5 Security

Static configuration checks are useful but do not constitute proof that the Electron application is secure.

---

# 19. Connector Verification

## 19.1 Purpose

Verify that application infrastructure uses approved connector mechanisms.

## 19.2 HTTP Checks

Detect supported direct usage patterns and compare them against approved architecture policy.

## 19.3 External CLI Checks

Identify direct process spawning outside approved framework boundaries.

## 19.4 SQLite Checks

Evaluate whether database connection lifecycle follows the selected persistence policy.

## 19.5 WebSocket Checks

Inspect supported connection creation and lifecycle patterns.

## 19.6 Filesystem Checks

Verify relevant approved path and artifact interfaces where detectable.

## 19.7 Application Adapters

Service-specific adapters may use framework connector interfaces.

The verifier shall not require domain services to depend directly on connectors.

## 19.8 Exceptions

Legacy direct connector usage may be temporarily baselined during migration.

It must remain visible as a violation until corrected or explicitly accepted under a permitted exception policy.

---

# 20. State Architecture Verification

## 20.1 Purpose

Verify state-management conventions.

## 20.2 Static Checks

Examples:

- State definitions declare scopes.
- Persistent state declares an adapter.
- Domain modules do not depend on concrete state stores.
- Framework-owned state namespaces are protected.
- Unsupported direct state mutations are detected.
- Application services do not retain invalid shorter-lived dependencies.

## 20.3 Concurrency Verification

Static analysis may identify suspicious patterns.

It cannot fully prove thread safety or absence of lost updates.

## 20.4 Runtime Checks

Executable tests may verify:

- Concurrent updates.
- Compare-and-set.
- Persistence.
- Restoration.
- Subscription cleanup.
- Renderer synchronization.

## 20.5 Durability

The verifier must not treat the existence of a SQLite database as proof that all relevant state mutations are durable.

---

# 21. Job and Process Verification

## 21.1 Purpose

Verify managed execution ownership and process lifecycle conventions.

## 21.2 Static Checks

Examples:

- Job definitions use the Job Manager.
- External processes use framework process facilities.
- Queue limits are declared.
- Execution strategies are configured.
- Job persistence policies are consistent.
- Recovery policies exist where required.

## 21.3 Durable Execution Claims

An application must not claim durable job execution solely because it stores job records.

## 21.4 Cancellation

Static inspection cannot prove that non-cooperative work terminates.

Runtime tests are needed for cancellation behavior.

## 21.5 Process Cleanup

The presence of a process cleanup method does not prove that all processes are cleaned up.

## 21.6 Result

The verifier shall distinguish:

- Structural adoption.
- Configured lifecycle policies.
- Executed behavioral evidence.

---

# 22. Configuration and Lifecycle Verification

## 22.1 Configuration Rules

Potential checks:

- Configuration schema is valid.
- Required settings exist.
- Environment selection follows policy.
- Known embedded secrets are prohibited.
- Optional capabilities are not unnecessarily configured.
- Production paths avoid unsupported development assumptions.

## 22.2 Composition Rules

Potential checks:

- Dependency registrations are valid.
- No known dependency cycles.
- Required components are registered.
- Scope relationships follow policy.

## 22.3 Lifecycle Rules

Potential checks:

- Managed resources have lifecycle contracts.
- Runtime bootstrap uses approved lifecycle facilities.
- Shutdown is coordinated through the framework.
- Required initialization dependencies are declared.

## 22.4 Runtime Proof

Initialization order, cleanup correctness, and readiness behavior require executable evidence where the rule is behavioral.

# 23. Test-Evidence Integration

## 23.1 Purpose

Some architectural requirements cannot be verified statically.

The verifier should support trusted test evidence.

## 23.2 Evidence Categories

Possible inputs:

- Unit test results.
- Integration test results.
- CLI protocol contract results.
- Electron integration test results.
- Process lifecycle tests.
- Persistence tests.
- Security tests.

## 23.3 Trusted Evidence

Test evidence must identify:

- Test identifier.
- Test runner.
- Execution timestamp.
- Relevant source revision.
- Execution environment.
- Actual result.
- Output artifact or report reference.

## 23.4 Stale Tests

Test results from an unrelated source revision must not automatically prove the current implementation.

## 23.5 No Execution by Default

Default static verification shall not execute project code.

An explicit verification mode may run approved tests.

## 23.6 Test Result Semantics

A passing test demonstrates that the tested behavior passed under its recorded conditions.

It does not prove all untested execution paths are correct.

## 23.7 Missing Tests

Required but unexecuted tests shall produce NOT_CHECKED for behavior-dependent rules unless stronger relevant evidence is available.

# 24. Rule Severity

## 24.1 Purpose

Severity communicates the architectural impact of a violation.

## 24.2 Proposed Levels

| Severity | Meaning |
|---|---|
| Critical | Fundamental safety or runtime integrity concern |
| High | Significant architectural boundary violation |
| Medium | Maintainability or integration concern |
| Low | Minor architectural convention |
| Informational | Observation or improvement guidance |

## 24.3 Severity Versus Verdict

Severity and verification outcome are separate.

A critical rule may be NOT_CHECKED.

A low-severity rule may FAIL.

## 24.4 Enforcement

CI failure policy shall consider rule outcome, severity, profile policy, and approved exceptions.

## 24.5 Severity Overrides

Profiles may adjust allowed severities where permitted.

Mandatory framework security constraints must not be downgraded through arbitrary application-level configuration.

# 25. Architecture Exceptions

## 25.1 Purpose

Some applications may have legitimate reasons to deviate from a rule.

The architecture must support explicit and reviewable exceptions.

## 25.2 Exception Requirements

Each exception should identify:

- Rule ID.
- Rule version or compatible range.
- Affected application or source scope.
- Justification.
- Responsible owner.
- Approval reference.
- Creation date.
- Expiration or review policy.
- Evidence of mitigating controls, where applicable.

## 25.3 Example

```yaml
exceptions:
  - id: EX-001
    rule: APP-006

    scope:
      path: src/legacy/integration.py

    reason: Transitional adapter during migration

    owner: application-team
    approved_by: architecture-review
    expires: 2027-03-31
```

This is illustrative.

## 25.4 Exception Validation

The engine shall detect:

- Unknown rules.
- Invalid scopes.
- Expired exceptions.
- Missing required approval.
- Unsupported exception types.
- Attempts to waive nonwaivable constraints.

## 25.5 Exception Effects

An approved exception does not change a FAIL verdict into PASS.

The verifier shall preserve the raw rule outcome and separately record the exception's enforcement effect.

## 25.6 Mandatory Rules

Some rules may be nonwaivable under the normal application exception mechanism.

These should include critical framework integrity and security constraints.

## 25.7 Expiration

Expired exceptions shall cease to suppress enforcement according to policy.

## 25.8 Governance

The engine validates exception metadata but cannot independently prove that a claimed approval was authorized unless integrated with a trusted approval mechanism.

# 26. Migration Baselines

## 26.1 Purpose

Existing applications may initially violate many target architecture rules.

A baseline allows incremental migration without hiding the existing violations.

## 26.2 Baseline Principle

**A baseline permits controlled progress toward compliance; it does not establish compliance.**

## 26.3 Baseline Contents

A baseline should record:

- Profile and version.
- Rule versions.
- Baseline source snapshot.
- Existing violation fingerprints.
- Severity.
- Source references.
- Creation metadata.
- Optional remediation ownership.

## 26.4 Example

```json
{
  "schema_version": "1.0",
  "profile": "ddd",
  "baseline": {
    "source_revision": "abc123",
    "violations": [
      {
        "rule_id": "APP-006",
        "fingerprint": "violation-fingerprint",
        "source_path": "src/legacy/service.py"
      }
    ]
  }
}
```

This is illustrative.

## 26.5 New Violations

The verifier shall identify violations not present in the approved baseline.

## 26.6 Resolved Violations

Previously recorded violations that are no longer present shall be reported as resolved.

## 26.7 Persistent Violations

Existing baseline violations shall remain visible.

They may be classified separately from newly introduced violations for enforcement.

## 26.8 Baseline Drift

The framework should detect obsolete or stale baseline entries.

## 26.9 Baseline Revisions

Updating the baseline must be an explicit operation.

Ordinary verification shall not silently rewrite baseline files.

## 26.10 Security Constraints

Baselines must not be permitted to suppress nonwaivable security requirements under ordinary enforcement policies.

## 27.2 Fingerprint Inputs

- Rule ID.
- Architectural entity identity.
- Relevant dependency relationship.
- Normalized source context.
- Violation category.

## 27.3 Stability

## 27.4 Refactoring

## 27.6 Baseline Correctness

Comparison should use enough context to avoid treating a newly introduced violation as an old baseline violation merely because the same rule ID appears.

# 30. Enforcement Policy

## 30.1 Purpose

The enforcement engine determines whether verification results satisfy a selected quality gate.

## 30.2 Separation from Verdicts

A rule's verdict describes what was established.

Enforcement determines whether the result is acceptable for a particular workflow.

## 30.3 Proposed Enforcement Modes

### Advisory

Report findings without blocking the workflow.

### Standard

Block selected new or unexcepted violations according to configured severity.

### Strict

Require all mandatory applicable rules to pass and disallow unresolved mandatory checks.

### Migration

Allow approved baseline violations while preventing new violations and enforcing nonwaivable constraints.

## 30.4 Proposed Policy Example

```yaml
verification:
  mode: migration

  enforcement:
    fail_on:
      - critical
      - high

    block_new_violations: true
    allow_approved_baseline: true

    unresolved_required_rules: fail
```

This is illustrative.

## 30.5 Unresolved Checks

For mandatory rules, NEEDS_REVIEW and NOT_CHECKED must not silently satisfy strict compliance gates.

## 30.6 Enforcement Result

Possible aggregate enforcement statuses:

- `passed`
- `failed`
- `incomplete`
- `error`

These are separate from rule verdicts.

## 30.7 Incomplete Verification

When mandatory evidence is missing, the result should be `incomplete` unless the selected enforcement policy explicitly treats that condition as a blocking failure.

# 39. End-to-End Validation Scenarios

## AV-S01 — Compliant Minimal Application

**Given** a minimal AdharaSutra application,

**When** its profile-specific rules execute,

**Then** the verifier shall not require unused DDD layers or optional connector infrastructure.

**And** applicable rules shall report evidence-backed outcomes.

## AV-S02 — DDD Dependency Violation

**Given** a domain module imports a concrete infrastructure implementation,

**When** dependency verification runs,

**Then** the applicable rule shall report FAIL with source evidence.

## AV-S03 — Incomplete Source Analysis

**Given** relevant source cannot be parsed,

**When** a rule depends on that source,

**Then** the verifier shall not report PASS merely because no violation was detected.

## AV-S04 — Electron Renderer Violation

**Given** a renderer directly starts a Python subprocess,

**When** Electron architecture verification runs,

**Then** the relevant rule shall report a violation.

## AV-S05 — Direct External Process Execution

**Given** an application directly invokes subprocess infrastructure outside approved boundaries,

**When** the selected profile requires the Process Connector,

**Then** the verifier shall identify the violating source location.

## AV-S06 — Optional Connector Not Selected

**Given** an application does not use SQLite,

**When** verification runs,

**Then** SQLite-specific requirements shall be nonapplicable unless another selected capability requires them.

## AV-S07 — Missing Runtime Evidence

**Given** a behavioral rule requires an executable test,

**When** no compatible test result is available,

**Then** the rule shall report NOT_CHECKED.

## AV-S08 — Approved Exception

**Given** a rule violation has a valid approved exception,

**When** enforcement runs,

**Then** the underlying result shall remain FAIL.

**And** the report shall separately identify the accepted exception.

## AV-S09 — Expired Exception

**Given** an exception has expired,

**When** enforcement runs,

**Then** it shall no longer suppress the violation.

## AV-S10 — Migration Baseline

**Given** a legacy application has approved baseline violations,

**When** migration-mode verification runs,

**Then** existing violations shall remain visible.

**And** new violations shall be identified separately.

## AV-S11 — Resolved Baseline Violation

**Given** a previously recorded violation has been corrected,

**When** verification runs,

**Then** the baseline comparison shall report it as resolved.

## AV-S12 — New Critical Security Violation

**Given** a new nonwaivable critical rule violation appears,

**When** verification runs under migration policy,

**Then** an ordinary baseline or exception shall not make the violation acceptable.

## AV-S13 — Stale Evidence

**Given** a source file changes after discovery,

**When** verification attempts to reuse old evidence,

**Then** the affected evidence shall be rejected or refreshed.

## AV-S14 — Generated Project Verification

**Given** AdharaSutra generates a new application,

**When** the verifier evaluates its selected architecture profile,

**Then** its generated foundation shall satisfy applicable structural rules, assuming successful and complete generation.

## AV-S15 — Custom Evaluator Failure

**Given** a custom rule evaluator raises an unexpected exception,

**When** verification executes,

**Then** affected rules shall report NOT_CHECKED or an equivalent explicit execution failure.

**And** unrelated rule results shall remain valid where possible.

## AV-S16 — CI Failure

**Given** a blocking rule fails,

**When** the CI verification command executes,

**Then** the developer CLI shall return the configured nonzero failure exit code.

## AV-S17 — Cross-Agent Verification

**Given** different coding agents operate on the same source snapshot,

**When** they run the same verifier and profile versions,

**Then** canonical rule verdicts shall be equivalent.

## AV-S18 — No Automatic Repair

**Given** a verification report contains violations,

**When** the verifier completes,

**Then** application source files shall remain unchanged.

# 41. Outstanding Questions

## AV-OQ-001 — Rule Definition Language

Should the initial rule engine support a declarative YAML rule format, Python rule classes, or both?

**Recommendation:** Use declarative definitions for common checks and trusted Python evaluators for complex rules.

## AV-OQ-002 — Profile Configuration

Should profiles be stored in the same package as scaffolding templates?

**Recommendation:** Maintain shared profile contracts independently from template rendering and verification execution.

## AV-OQ-003 — Runtime Evidence

Should `adhara verify` execute tests by default?

**Recommendation:** No. Default to static verification and add an explicit test-enabled mode.

## AV-OQ-004 — Baseline Storage

Should migration baselines be committed to the application repository?

**Recommendation:** Support repository-local committed baselines when teams need reviewable architecture debt, while permitting explicit external baseline paths.

## AV-OQ-005 — Exception Approval

How should approval authority be verified?

**Recommendation:** Begin with reviewable exception files and documented governance. Do not claim cryptographic or organizational approval verification without a trusted approval integration.

## AV-OQ-006 — Mandatory Security Rules

Which rules should be nonwaivable?

**Recommendation:** Define a narrowly scoped core safety policy covering arbitrary process execution, protected protocol boundaries, and other genuine framework-integrity requirements.

## AV-OQ-007 — Enforcement Defaults

Should standard verification fail on high and critical violations?

**Recommendation:** Yes, subject to finalized profile and rule governance.

## AV-OQ-008 — NEEDS_REVIEW Policy

Should unresolved high-severity rules block CI?

**Recommendation:** Require review or additional evidence for mandatory high-severity rules; do not silently accept unresolved results.

## AV-OQ-009 — Baseline Fingerprints

How stable should fingerprints be across source refactoring?

**Recommendation:** Use semantic relationship information where feasible, with explicit handling for ambiguous cross-revision matching.

## AV-OQ-010 — Rule Version Changes

Should rule upgrades automatically invalidate existing baselines?

**Recommendation:** Reevaluate affected baselines and flag compatibility changes instead of silently preserving outdated suppressions.

## AV-OQ-011 — Incremental Verification

Should incremental rule evaluation ship in the first implementation?

**Recommendation:** Start with reliable full verification and reuse valid discovery caches; add rule-result caching only after correctness tests are established.

## AV-OQ-012 — SARIF Support

Should verification reports support SARIF for code-hosting annotations?

**Recommendation:** Add SARIF as an optional reporting format after the canonical JSON model stabilizes.

## AV-OQ-013 — Documentation Rules

Should missing project documentation block architecture verification?

**Recommendation:** Treat documentation rules as profile-dependent, usually lower-severity constraints unless the missing contract is essential.

## AV-OQ-014 — Cross-Repository Verification

Should shared packages be verified across multiple repositories?

**Recommendation:** Support monorepo boundaries initially and defer multi-repository dependency verification until required.

## AV-OQ-015 — Rule Performance

Should custom evaluators run in isolated subprocesses?

**Recommendation:** Evaluate this for trusted plugin fault isolation, while recognizing that subprocess execution alone is not a sandbox.

## AV-OQ-016 — Architecture Debt Reporting

Should verification track violation trends across commits?

**Recommendation:** Support comparison of saved verification reports, while keeping historical analytics optional.

- [ ] Verification is distinct from discovery.
- [ ] The shared architecture model is the primary input.
- [ ] Architecture profiles are versioned.
- [ ] Profile composition is defined.

- [ ] Rule identifiers and versions are stable.
- [ ] Rules define applicability.
- [ ] Rules declare evidence requirements.
- [ ] Deterministic evaluation semantics are defined.

- [ ] Nonapplicable rules are excluded from compliance counts.
- [ ] Incomplete discovery cannot create false PASS outcomes.
- [ ] Source evidence freshness is validated.
- [ ] Structural checks are defined.
- [ ] Dependency checks are defined.

# 45. Final Architecture Summary

AdharaSutra's Architecture Verification subsystem evaluates existing application implementations against versioned architecture standards.

It uses the Architecture Discovery subsystem's source-backed ApplicationArchitecture model as its primary evidence foundation.

The engine manages:

- Architecture profile selection.
- Rule applicability.
- Evidence requirements.
- Deterministic rule evaluation.
- Violation classification.
- Severity.
- Exceptions.
- Migration baselines.
- Enforcement.
- Reporting.

Its four canonical rule verdicts are:

- PASS.
- FAIL.
- NEEDS_REVIEW.
- NOT_CHECKED.

The verifier must never assume compliance merely because no violation was detected in incomplete source analysis.

Approved exceptions and migration baselines affect enforcement but do not erase underlying violations.

Behavioral guarantees require compatible runtime or test evidence.

The subsystem supports developer CLI usage, CI quality gates, and coding-agent workflows while remaining read-only and independent of LLM inference.

The central guarantee is:

**Every architecture verdict is tied to an explicit rule, a versioned profile, and sufficient evidence—or is clearly marked as unresolved.**
